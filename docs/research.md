# Stack Research — First Mountain Construction (2026-10-14)

Archetype: static / brochure with lead capture, image-heavy filterable gallery (46 real job photos), motion-forward, local SEO. No CMS, accounts, DB, payments or server code in the preview.
Every version below was checked on 2026-10-14 with `npm view` (Node v24.21.0, npm 11.19.0 on this machine) unless marked (unverified). Zydeco (2026-10-06) and Corvis (2026-10-07) research was reused where it still holds; every version and every release since 2026-10-06 was re-checked. Browser support figures come from `@mdn/browser-compat-data` 8.1.5 (published 2026-10-08), read directly from its JSON. Image timings were measured on this machine with sharp 0.35.5 against a real photo from this client (#00, 5712x3213 iPhone original).

## Requirements that drive the choice

1. **Phones first, fast, and SEO-critical for local search.** Six static pages, tap-to-call and tap-to-text everywhere, LocalBusiness JSON-LD, sitemap, LCP under 2 s on throttled mobile, CLS under 0.02, WCAG 2.2 AA.
2. **46 large phone originals** (3000–5712 px, 2–10 MB each, GPS EXIF inside) must become a small repo, fast builds and light pages. The gallery must be filterable with a lightbox and no layout shift. Five photos are ≤960 px and must never be upscaled.
3. **"Rugged premium" motion** (GSAP screed reveals, parallax, pinned process) that never hides content without JS, respects reduced motion, and doesn't hurt INP.
4. **The quote form is a validated UI now and gets wired later** on the same Cloudflare project, with the same schema.
5. **Real Google reviews and a map**, shown without breaking Google's structured-data rules and without loading third-party trackers by default.
6. **Free Cloudflare static hosting, Windows 11 with Node 24 and npm only**, the fewest accounts, and consistency with the sibling sites (grit, zydeco, corvis) so code and tests carry over.

## Q2. Image pipeline for 46 large originals

**Finding that changes the plan:** the originals folder from intake (`…/9c8022d7…/scratchpad/photos`) is now **empty**, so the photos must be re-fetched from `docs/google-photo-urls.txt`. Testing photo #00 today:

| URL suffix                        | Result                                                                                                  |
| --------------------------------- | ------------------------------------------------------------------------------------------------------- |
| none                              | 512x288 thumbnail, 44 KB                                                                                |
| `=s0`                             | original 5712x3213, 3.8 MB, **EXIF includes GPS-Data and "iPhone 16 Pro"** (a customer's home location) |
| `=s2400` (same as `=w2400-h2400`) | 2400x1350, 696 KB, EXIF stripped to 2 Picasa tags                                                       |
| `=s2400` on low-res #06           | 720x960 (Google does not upscale)                                                                       |

**Recommendation: `npm run images:prepare` (`scripts/prepare-images.mjs`, one-off, not part of the build).**

- Read `docs/google-photo-urls.txt` and fetch each `<url>=s2400`. Google resizes server-side, so we skip downloading 2–10 MB originals.
- Pipe each image through sharp: `.autoOrient()`, resize `fit: 'inside'`, 2400 px max, `withoutEnlargement`, sRGB, `.jpeg({ quality: 82, mozjpeg: true })`. sharp drops all metadata by default (verified: `exif` undefined on output). Write `src/assets/photos/<id>.jpg` (zero-padded id from the URL list).
- Write `src/assets/photos/manifest.json` with id, width, height and source URL. `gallery.ts` (orchestrator-owned) adds alt, category, featured, focal point and `lowRes` (derived from width <1000, and a unit test enforces it).
- Optional `--from <dir>` flag to process local originals instead of fetching, with the same output. Never commit raw originals (GPS). Add a unit/CI assertion that no file in `src/assets/photos` carries EXIF GPS (sharp `metadata()`).
- Idempotent: skip ids that already exist unless `--force`.

**Measured costs (sharp 0.35.5 / libvips 8.18.7, this machine, single-threaded call per encode):**

- Original → 2400 px mozjpeg q82: 498 ms, **416 KB** (from 3.8 MB).
- AVIF q50: 640 w 144 ms / 14 KB · 1080 w 226 ms / 40 KB · 1600 w 345 ms / 89 KB · 2400 w 624 ms / 205 KB.
- WebP q75: 640 w 42 ms / 21 KB · 1080 w 76 ms / 62 KB · 1600 w 137 ms / 136 KB · 2400 w 223 ms / 270 KB.

**Repo size:** about 46 x 0.3–0.7 MB ≈ **15–25 MB** committed (the five low-res files are ~0.1 MB each), compared with ~150–250 MB for raw originals. Acceptable for git. If the owner later supplies 40+ more photos, consider Git LFS or capping at 2000 px.

**Build time (estimate from the measurements above):** per photo, grid tiles at about 5 widths x (AVIF + WebP) ≈ 1.5 s CPU, plus 3 lightbox AVIF widths ≈ 1.2 s, so ≈ 2.7 s CPU per photo, ≈ 125 s CPU for 46, plus ~30% for home/services/hero reuse. Astro processes images concurrently, and sharp reports concurrency 16 here, so expect a **cold build of ~45–120 s** and a **warm build of ~10–20 s**. Optimised outputs are cached in `node_modules/.astro/assets` (zydeco's cache is 248 MB, so it stays out of git, which is fine). Formats matter: zydeco's default AVIF + WebP + JPEG produced 52 MB of WebP alone. Dropping the JPEG tier and using AVIF for the lightbox saves both time and bytes.

**dist size:** about 0.7–0.9 MB of derivatives per photo ≈ **35–45 MB, ~600 files** (limits: 20,000 files and 25 MiB per file). **Gotcha confirmed in zydeco (Astro 7.3.6):** unreferenced source images are still emitted to `dist/_astro`. Zydeco's dist had 34 JPGs (16 MB) and 5 PNGs (26 MB) with zero HTML references, which is why zydeco has `scripts/prune-dist.mjs`. Copy that script and run it in `deploy`/`build:prune`. Keeping sources at ≤2400 px also keeps any leaked originals small. Never pass an imported image's `.src` (the original) to PhotoSwipe or the OG tag; always go through `getImage()`.

**Per-image rules:** hero (#04) is eager with `fetchpriority="high"` and `sizes="100vw"`, the only eager image on the page. Everything else uses `loading="lazy"` and `decoding="async"`. Low-res items get `widths` capped at their native width and a smaller tile (never full-bleed). Photo #26 (highway) is atmospheric only and is not in the gallery.

### Q2b. Masonry?

- `display: grid-lanes` (the final masonry syntax): **Safari 26.4 / iOS 26.4 only**. Chrome, Edge and Firefox: `false` in BCD (flag or nightly only, still migrating from the old `grid-template-rows: masonry` syntax). MDN marks it experimental and not Baseline. Chrome on Android is most of this audience, so masonry would be invisible to most visitors.
- CSS multi-column fallback: visual order runs down each column while DOM/tab order runs across. That breaks the meaningful focus sequence (WCAG 2.4.3) and makes filtering reshuffle columns unpredictably. Rejected.
- JS masonry libraries (Masonry.js etc.): add JS and CLS. Rejected.
- **Decision:** a uniform aspect-ratio grid (1 column on phones, 2 at 48 rem, 3–4 at 64 rem+), cropped tiles with a manifest focal point, and the full uncropped photo in the lightbox. This gives zero CLS, predictable filtering and correct focus order. A `@supports (display: grid-lanes)` enhancement can be added later in one CSS block if the design wants natural aspect ratios on Safari. It is not in the MVP because it doubles the visual QA surface for a minority of browsers.

## Q3. View transitions: worth it, and which kind

**Yes, use native cross-document transitions. Do not use `<ClientRouter />`.**

- Support (BCD 8.1.5): `@view-transition` Chrome/Edge 126+, Safari/iOS 18.2+, Firefox **not supported** (same-document `startViewTransition` reached Firefox 144, cross-document did not). Unsupported browsers ignore the at-rule and navigate normally. MDN marks it as not Baseline, which is fine for pure progressive enhancement.
- Cost: a few lines of CSS, zero JS. It makes six static pages feel like one app (header stays put, content crossfades), which is the "polish" the client will notice on a phone.
- Why not `<ClientRouter />`: it turns the site into a SPA. Astro's docs say bundled scripts then run only once, so GSAP ScrollTriggers, the pinned process section, the gallery filter, PhotoSwipe, the mobile menu and the open-now badge would all need `astro:page-load` / `astro:before-swap` init and teardown, which is the classic source of leaked or misplaced ScrollTriggers. Astro's own docs say the ClientRouter is becoming "increasingly unnecessary" as browsers ship native APIs. Its benefits (persisted state, Firefox animation) don't matter for this brief.
- GSAP interplay (implementation rules for the spec):
  1. Wrap the opt-in: `@media (prefers-reduced-motion: no-preference) { @view-transition { navigation: auto; } }`.
  2. Name only a few stable elements (`site-header`, optionally `page-title`). Don't name gallery tiles: 46 snapshots are costly and names must be unique.
  3. Keep the root transition short (≈200–250 ms fade/slide). Start the hero/heading GSAP entrance on `pagereveal` after `event.viewTransition?.finished` when present, otherwise immediately (Firefox has no `PageRevealEvent`, so feature-detect). This stops GSAP from animating elements while they are still being captured.
  4. Each page is a fresh document, so ScrollTrigger needs no teardown. Test back/forward (bfcache restore) once: call `ScrollTrigger.refresh()` on `pageshow` when `event.persisted`.
  5. Keep final states in CSS so the snapshot of a no-JS page is already correct.
- The Playwright reduced-motion project covers the off state. Visual checks of the transition are manual (Chrome + Safari).

## Q5. Reviews and JSON-LD

**Do not emit `aggregateRating` or `review` structured data.** Show the reviews as visible HTML only, with a "Read all reviews on Google" link.

- Google's review-snippet doc (last updated 2026-09-08): "If the entity that's being reviewed controls the reviews about itself, their pages that use LocalBusiness or any other type of Organization structured data are ineligible for star review feature." So there is no rich-result benefit.
- The same doc: "Don't aggregate reviews or ratings from other websites" and, for local businesses, "Ratings must be sourced directly from users." Our 4.7★ / 30 and the review texts come from Google Maps, so marking them up is aggregation from another site, which is a guideline violation that "may" draw a manual action (structured data then ignored). That is all risk and no reward.
- Google's LocalBusiness doc (updated 2026-09-08) lists `aggregateRating`/`review` only "for sites that capture reviews about other local businesses". Required: `name`, `address`. Recommended: `geo` (≥5 decimals), `openingHoursSpecification` (hh:mm:ss), `telephone` with country code, `url`, `priceRange` (omit; unknown). Use the most specific subtype, which is `GeneralContractor` (a schema.org subtype of HomeAndConstructionBusiness), and don't stack redundant parent types.
- Visible UI: the rating summary shows "4.7 from 30 Google reviews, as of Oct 2026" from `site.ts` (one source), links to the listing, and shows only 5★ texts as the brief requires. The page must not imply the count covers only the shown reviews.

## Alternatives considered

- **Same stack with plain tokenised CSS** (refined-celebrations style): viable runner-up if the designer prefers hand-authored CSS. Tailwind is kept for sibling consistency and iteration speed.
- **Next.js 16 static export / SvelteKit / React Router**: ship a runtime, weaker static image pipeline, no gain for six static pages.
- **`<ClientRouter />`**: see Q3. Revisit only if a persistent element (e.g. audio, or a map that must survive navigation) is ever required.
- **Motion 14.2.0** instead of GSAP: lighter but weaker for timelines and pinning. Do not mix the two.
- **Lenis 1.3.26**: scroll hijacking hurts a11y, anchors and focus. Skipped.
- **GLightbox 3.3.1 / Fancybox**: PhotoSwipe is proven in-house and stronger on touch and a11y. Fancybox has commercial licence complexity.
- **Masonry (`grid-lanes`, CSS columns, Masonry.js)**: see Q2b.
- **Cloudflare Images / Cloudinary / Google `=sNNN` URLs hot-linked at runtime**: hot-linking Google's CDN means depending on unofficial URLs that can expire and loses AVIF/srcset control. An image CDN adds an account. Build-time astro:assets is free and deterministic.
- **Committing raw originals or Git LFS**: 150–250 MB with GPS EXIF. Rejected. Fetch `=s2400` and re-encode.
- **Picture with default AVIF + WebP + JPEG**: no browser in the support matrix needs JPEG. It is slower to build and bigger in dist.
- **Embedding Google reviews via a widget (Elfsight, etc.)**: third-party JS, still self-serving for Google, account and cost. Static typed data is faster and accessible.
- **Maps Embed API with key / Static Maps**: see Q4.
- **TypeScript 7.0.2**: blocked by `@astrojs/check` and typescript-eslint peer ranges.
- **@astrojs/cloudflare 14.3.4 adapter**: only for SSR. The later Worker route doesn't need it.
- **astro 7.4.0-beta.1**: beta. Stay on 7.3.x.

## Accounts, costs & env vars needed

- **Now: none.** No paid services, no API keys (the map uses the keyless share-embed behind a facade).
- `.env.example`: `PUBLIC_SITE_URL` (preview URL; canonical/OG/sitemap), `PUBLIC_FORM_ENDPOINT` (empty = demo mode).
- Network at build time: the Fonts API fetches from Fontsource on the first build (cached afterwards). `images:prepare` fetches from `lh3.googleusercontent.com` once.
- **Later, each with explicit user confirmation:** Cloudflare account (free; the user already has one, see memory notes), Resend + verified domain (`RESEND_API_KEY`, `QUOTE_TO_EMAIL`; free 100/day, 3,000/month per zydeco research), Turnstile (`PUBLIC_TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET_KEY`; free plan unlimited per corvis research), and the client's domain/DNS.
- Rights: photos and review text come from the client's public Google profile, for preview use only. Get the client's written OK before launch, and keep `source` per photo in the manifest.

## Risks / open questions

1. **Image volume vs build/deploy time and size.** 46 photos x many derivatives is the heaviest part of this site. Mitigation: ≤2400 px sources, AVIF-only `<Picture>` with WebP fallback, capped `widths`, the cache in `node_modules/.astro`, `prune-dist`, and recording real cold/warm build times and dist size in progress.md after the first build (estimates here: 45–120 s cold, 35–45 MB dist).
2. **Privacy and rights of the photos and reviews.** Google originals carry GPS EXIF (customers' homes). `images:prepare` must strip metadata, and a test must assert it. The photos and review texts are the client's and reviewers' content, for preview only until the client approves. Rating counts go stale, so show an "as of" date.
3. **Version churn:** @playwright/test 1.64.1 and wrangler 4.151.0 were published today, and Astro 7.3.8 changed its internal bundler. Pin with `^` and commit the lockfile. TS 7 is still blocked. Progressive features (cross-document view transitions, scroll-driven CSS, grid-lanes) are absent in Firefox, so everything must degrade to a normal, fully visible page.
4. Unconfirmed business facts (phone 925 area code, fence service, 20+ years, service area) stay in `site.ts` with `// confirm` and feed the JSON-LD from that one place.
5. Unverified here: the exact payload weight of the Google Maps iframe, Google Maps ToS wording on storing screenshots, Archivo's width axis, and Astro's `<Picture>` `priority` prop (use explicit `loading="eager" fetchpriority="high"` if it isn't there).
